# Трекер питания

Типовой сценарий для нового пользователя Live OS. Перед созданием вызови `list_trackers`: если дневник питания уже существует, используй его схему и не создавай дубль.

Для нового дневника создай `log` трекер `meals` с позициями `items` и серверными итогами `totals` через `x-sum-of`. Пример схемы:

```json
{
  "type": "object",
  "properties": {
    "meal_type": {
      "type": "string",
      "enum": ["breakfast", "lunch", "dinner", "snack"]
    },
    "items": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "name": { "type": "string" },
          "grams": { "type": "number", "x-unit": "g", "minimum": 0 },
          "kcal": { "type": "number", "x-unit": "kcal", "minimum": 0 },
          "protein": { "type": "number", "x-unit": "g", "minimum": 0 },
          "fat": { "type": "number", "x-unit": "g", "minimum": 0 },
          "carbs": { "type": "number", "x-unit": "g", "minimum": 0 },
          "source": {
            "type": "string",
            "enum": ["label", "manual", "model_estimate"]
          }
        },
        "required": ["name", "grams"]
      }
    },
    "totals": {
      "type": "object",
      "x-sum-of": "items",
      "properties": {
        "kcal": { "type": "number", "x-unit": "kcal", "minimum": 0 },
        "protein": { "type": "number", "x-unit": "g", "minimum": 0 },
        "fat": { "type": "number", "x-unit": "g", "minimum": 0 },
        "carbs": { "type": "number", "x-unit": "g", "minimum": 0 }
      }
    }
  },
  "required": ["meal_type", "items"]
}
```

Записывай значения за съеденную порцию. До любого расчёта новой позиции вызови `list_templates` для дневника питания: сначала используй только явно совпадающий пользовательский продукт или рецепт и масштабируй его по порции, подтверждённой в текущем сообщении. Шаблон не доказывает порцию и не подходит по приблизительному совпадению названия. Если такого шаблона нет, используй читаемую текущую этикетку; если и её нет, но продукт и порция ясны, сделай прозрачную оценку с `source: model_estimate` и назови её оценкой в подтверждении. Уточни одним вопросом только неясный продукт или порцию. Для этикетки на 100 г сначала масштабируй по фактической массе; сохраняй исходные значения и расчёт в примечании или связанном шаблоне. Массу или объём новой позиции бери только из явной пары «продукт — количество» текущего сообщения, читаемого текущего изображения, либо из прямой команды пользователя повторно применить ранее указанную порцию. История чата сама по себе не является источником порции; нельзя переносить число от другого продукта или приёма. Масса нетто упаковки также не означает, что съедена вся упаковка. Если связь продукта и порции неочевидна, уточни её до записи этой позиции; остальные однозначные позиции можно сохранить. Неизвестная пищевая ценность не равна нулю: записывай `0` ккал или нулевой макронутриент только когда это прямо указано пользователем или читается на текущей этикетке, либо это вода или явно напиток без добавок (например, несладкий чай или чёрный кофе). Напиток, в котором возможны молоко, сахар, сироп или другая добавка, не равен нулю. Отсутствие шаблона, неясная этикетка, неизвестный объём напитка или пропущенное поле остаются неизвестными; не создавай позицию с выдуманным `0` ккал. Неизвестные нутриенты оставляй отсутствующими. `source` у каждой позиции показывает происхождение; если существующая схема не поддерживает его, укажи источники по позициям в `note` и не меняй схему самостоятельно. После успешной записи можно один раз коротко предложить сохранить явно повторяемый продукт или блюдо как шаблон, если КБЖУ взяты с этикетки/фото, сообщил пользователь или есть прозрачная оценка с ясной порцией. Не предлагай это для разового блюда, уже использованного шаблона или повторно в том же разговоре; создавай шаблон только после согласия пользователя. Если пользователь сообщает о еде, съеденной сейчас, не передавай `occurred_at` и `local_date`: сервер записывает текущий момент в часовом поясе профиля. Сервер также понимает сегодняшнюю `local_date` без времени как событие сейчас. Если пользователь указал только время приёма (например, «ранний завтрак 6:30»), сначала возьми `today` из `get_context` и соедини это время именно с этой текущей локальной датой и часовым поясом профиля. История Telegram, preview недавних записей и приёмы вчера не являются источником даты. Другую дату передавай только для явно прошлой исторической записи; она честно останется с неизвестным временем, если время не названо.

Для повторяющегося продукта или рецепта предложи `create_template`: `kind` выбирается по смыслу (`food`, `recipe` или другой), `tracker_id` связывает шаблон с дневником, `data` хранит исходную порцию, ингредиенты и значения на 100 г без потери происхождения. Перед повтором вызови `list_templates`, учти нужную порцию, затем запиши новое событие через `add_entries`. Шаблон сам по себе не означает, что продукт был съеден.

Жидкость записывай в отдельный трекер лишь если такой учёт нужен пользователю. Напиток может одновременно входить в приём пищи и в объём жидкости; не складывай калории двух трекеров как независимые. Числовые итоги проверяй через `aggregate`. Для сводки можно создать карточки `create_dashboard_widget` по `totals.kcal`, `totals.protein` и другим полям, если пользователь хочет видеть их ежедневно.

После записи еды не ограничивайся сообщением «сохранил». Учитывай общие настройки общения и настройки проекта из `get_context`: `record_only` — краткое подтверждение, `brief` — одно полезное наблюдение, `coach` — более подробный разбор. Тон бери из `effective_conversation`. Даже в режиме подробного разбора не повторяй все поля записи без пользы.

Явный запрос «итог за день», «подведи итог» или сообщение о завершённом дне
переключает из режима записи в человеческую краткую рефлексию. Сначала прочитай
весь нужный день; отдели итог текущего приёма от дневного итога, признай одно
конкретное действие и добавь максимум одно наблюдение по сохранённой цели или
истории. Не оценивай еду морально, не придумывай норму и не начинай такой
разбор после каждого продукта.

Когда в одном сообщении пользователя несколько ясных позиций одного приёма, сначала разберись со всем сообщением и выполни **один** `add_entries` для всех ясных позиций (одна nutrition-запись с `items`, если это позволяет схема; иначе несколько entries в том же вызове). Не разделяй такой ввод на записи по одному продукту только ради расчёта. После успешного `add_entries` вызови `show_post_save`: передай `entry_id` последней созданной записи и все созданные в этом вызове IDs в `entry_ids`. Виджет покажет три разные области: «Добавлено сейчас», итог совпадающего приёма по группе и времени в дневнике, затем «За день». Не называй одну сохранённую позицию целым приёмом. Передавай `observation` только в режимах `brief`/`coach`, когда она опирается на известную дневную цель, план или агрегат: одна спокойная практичная строка. Не передавай observation для обычного перекуса. Для заметного перекуса, который занял существенную долю дневной цели или оставшегося лимита, можно нейтрально предложить скорректировать следующий приём пищи. Полную таблицу дня, круг БЖУ и графики показывай только по прямому запросу пользователя.

Если известны цели питания, сопоставь добавленный приём пищи с итогом за локальный день через `aggregate`, а не с суммой только этого блюда. `daily_targets` трекера показывают явно настроенные дневные цели; назови употреблённое, цель и остаток либо превышение с единицами. Если цель по КБЖУ не задана, не придумывай её из одного веса или желания похудеть. Предложи согласовать дневной ориентир и необходимые исходные данные, если пользователь хочет такой расчёт. Цель по весу и срок бери из относящихся к проекту записей; сравнивай с последним известным весом только после проверки даты и источника. Не обещай темп снижения веса по одной записи и не делай медицинских выводов.

Когда пользователь хочет увидеть питание за конкретный день, вызови `show_day_table` для дневника питания с `date` в локальном формате YYYY-MM-DD. Виджет показывает приёмы пищи, позиции, итоги каждого приёма и итог дня по серверному агрегату; без поддержки MCP Apps используй текстовый fallback. Если `truncated: true`, сообщи, что список позиций не полный. Для динамики веса используй отдельный `show_chart` с числовым полем датированного трекера веса, а не `baseline_weight_kg` профиля.

Капучино, кофе, декаф, латте и другие напитки могут быть позициями дневника питания, а не отдельным трекером жидкости. Перед ответом «не записано» или подсчётом чашек/объёма прочитай позиции питания за нужный период через `show_day_table` или `query_entries`; не делай вывод по одному названию трекера, краткому контексту или прошлому сообщению.

Если пользователь просит круговую диаграмму БЖУ за день, вызови `show_macro_pie`. Секторы — доли энергии из белков, жиров и углеводов по 4/9/4 ккал на грамм, а сохранённые калории показываются отдельно. Расхождение этих двух итогов не исправляй произвольно. При `incomplete`, `no_data` или `zero_energy` объясни причину отсутствия круга; не вычисляй проценты из частичных данных.

Похвала должна опираться на конкретное действие или прогресс, предупреждение — на подтверждённые данные и без осуждения. Если завтрак записан с оценочными КБЖУ, прямо обозначь неопределённость; при наличии дневной цели дай один практичный следующий шаг, а не длинную лекцию. При несовпадении данных, неполной дневной истории или отсутствии цели скажи об этом и задай один уточняющий вопрос лишь когда он реально поможет.
