# Working with medical documents in Live OS

Treat the original file, extracted text, proposed structured facts, and confirmed tracker entries as separate layers. When an attached file is clearly a laboratory report or analysis result and the client exposes it through the `save_file` attachment parameter, save it first with `folder_path: "health/analyses"`; verify the returned `file_id` before reading it. If the client exposes only a local attachment path, call create_file_upload with folder_path health/analyses, send the original bytes via its one-use PUT URL, and read the saved file ID from the response. A failed upload is not archival. A chat image that is only visible in model context is not automatically archived, so state that limitation rather than claiming it was saved. Before discussing a saved report, call `get_file` and, for image files, `read_image`; use `list_files` to find its ID. An `extraction_status` of `unavailable` or `failed` means there is no trustworthy text layer. For a scanned PDF, call `read_pdf_page` for each relevant page and identify visual readings as provisional. Do not infer unseen pages.

For each proposed laboratory result, keep the study date, literal test name, literal value, unit, reference interval from that report, source `file_id`, page/section when available, and any uncertainty. For a clinician's conclusion or prescription, preserve the original wording and distinguish a recommendation from what the user reports actually doing. Never replace a current medication or nutrition plan just because a later document was uploaded.

Show a compact review table before a bulk write. Mark uncertain, missing and illegible cells. Ask the user to confirm or correct the proposed rows, then write through the existing tracker tools with a new `client_request_id` and link the source file to the created entries with `attach_file`. On retries of the same approved write, reuse the same ID. `save_file` reuses an identical original for the same user by SHA-256; still search existing trackers and entries for a likely duplicate because equal bytes do not prove that two reports have identical meaning. If a user-owned medical tracker needs an extra optional field, read it with `list_trackers` and use `evolve_tracker_schema` with its `id` and current `version`; do not replace, rename, narrow, or make required an existing field.

Use a log tracker for dated measurements and a collection tracker for current plans or prescriptions. Create schemas from the actual data; keep medical-specific fields in those user-owned trackers, not in global profile fields or platform skills. A source-linked diet plan can guide discussion of nutrition records, but propose a change for the user and clinician to review rather than silently updating diet targets.

A mixed laboratory panel should preserve each result as printed, including a text value when the result is qualitative or its unit cannot be normalized. For a numeric trend, create or use a tracker for one comparable analyte and unit; do not aggregate different analytes or units together. A prescription can record clinician wording, start/end dates and status separately from a user's reported intake. A diet plan can record its source, effective period and restrictions separately from daily meals. Link every derived entry to the original `file_id` and keep page or section in the entry data so it remains inspectable in later conversations.

Do not diagnose, prescribe, change treatment or interpret a single laboratory result as a definitive conclusion. Report the document's own reference interval and unit; different laboratories may use different methods and ranges. Prepare questions for the treating clinician when values, wording or timing are unclear.
